# Repository security review — October 1, 2026

Reviewed baseline: `9377d6c58bed1cb50df728bf934ec8aa17c4b17c`.
This record distinguishes implemented repository changes from hosted settings
that still need independent verification. It is not a security certification.

## Repository changes

- Dependabot now covers all four application Dockerfiles, including Console
  and Service Pulse. Policy tests discover Dockerfiles instead of assuming a
  fixed directory list. Existing weekly updates and separated groups remain.
- Console's Node and Go build images are pinned to registry index digests.
  On October 1 the Docker registry response bytes matched each digest and both
  indexes included Linux AMD64 and ARM64. This is identity/architecture evidence,
  not a vulnerability scan of those images.
- PRs must successfully complete dependency review. Non-PR events skip that
  PR-specific check explicitly.
- All five publication jobs use the `release` environment, a shared publication
  concurrency group, read access to Actions evidence, and checkout without
  persisted credentials. Only the ForgeOps release publisher has contents-write.
- `scripts/validate-publication.py` requires the canonical repository, exact
  checkout SHA, an allowed event/ref, and a successful main-push Required
  Validation run with a successful Gate 4 job for that same commit. The newest
  run must succeed. Missing, incomplete or unavailable evidence fails closed.
  It waits at most ten minutes for main's concurrent validation to finish.
- Manual publication requires `main` plus a matching reviewed `source_sha`.
  Workbench and Console image publication now depend on their image-validation
  jobs; Restaurant and Pulse retain their validation dependencies.
- Versioned image publication requires the Docker Hub tag lookup to return
  exactly HTTP 404. Existing tags, authentication failures, rate limits and
  server/network errors prevent publication. Restaurant's deliberately moving
  `latest` and commit-SHA aliases are not semver release tags.
- ForgeOps publication creates a draft, downloads and compares the uploaded
  assets, publishes only after equality, and verifies release attestation.
  Existing tags/releases/assets are not rewritten by this change.

For manual image publication, select `main`, record its full reviewed commit
SHA as `source_sha`, and choose a new version. If main advances before dispatch,
the mismatch fails safely: review the new source and start a new run. A missing
or failed validation run must be resolved before retrying publication.
Service Pulse's corrective publisher remains intentionally limited to 0.1.1;
it is not a general-purpose release workflow and must be reviewed for a future
version. Its existing tag should continue to be rejected.

## Legacy release exception

The GitHub API reported `forgeops-v1.0.0` (September 19) as mutable and
`forgeops-console-v0.1.0-rc.1` (September 22) as immutable. Release-tag rules
protect both tags; tag rules alone do not protect legacy release asset bytes.
GitHub release immutability applies to future releases, not existing ones.

These public release assets were downloaded independently on October 1 and
hashed locally. The wheel matched the downloaded checksum file:

| Asset | Bytes | SHA-256 |
| --- | ---: | --- |
| `signalforge_forgeops-1.0.0-py3-none-any.whl` | 51589 | `be4d0a3001dac9bbbeec819327379461e27a7255557f6bdd66fd69d81ee7fc19` |
| `SHA256SUMS.txt` | 110 | `17212936c37ad55356267c25f41f8eb03262f3957e79f46a8c4747c5921593f5` |

These are observed bytes, not an independent historical trust anchor. They
cannot establish that no modification occurred before this review. Preserve
the legacy release and verify future downloads against the reviewed record.

## Administrative closeout — still unverified

The connector can read rulesets but cannot read the administrative inventories
or alert endpoint families needed below. Unknown does not mean disabled or
zero. Do not grant a new broad token merely to complete this checklist.

| Surface | Required review / target |
| --- | --- |
| Security alerts | Review open CodeQL, Dependabot and secret-scanning alerts; record counts by severity and dispositions without publishing secret values. Rotate any confirmed exposed credential. |
| Secret protection | Confirm repository secret scanning and push protection enabled; review bypasses and private vulnerability reporting. |
| Actions | Confirm read-only default token, Actions PR creation/approval disabled, appropriate fork approval requirements, allowed-action policy, and full-SHA enforcement. |
| Release environment | Confirm required owner review, administrator bypass policy, and explicit allowed refs: `main`, `forgeops-v*`, `forge-yaml-workbench-v*`, and `v*.*.*` as needed. Do not use an unrestricted environment. A sole maintainer may need self-review; document the exception rather than creating an unusable gate. |
| Credentials | Confirm Docker credentials are scoped to the release environment and minimum registry repositories; inspect expiry and rotation. Do not publish values. |
| Collaborators and apps | Inventory actual collaborators, pending invitations, installed GitHub Apps and their selected repositories/permissions. Confirm each business purpose before removing access. Review owner MFA/passkeys and recovery. |
| Deploy keys and webhooks | Confirm ownership, need, read-only keys where possible, webhook event scope, HTTPS/TLS verification and secret configuration; do not publish keys or webhook secrets. |
| Releases and tags | Confirm release immutability remains enabled. Existing rules prohibit tag changes/deletion; they do not restrict creation. Review tag creators and source policy with the owner's release procedure. |
| Registry | Verify registry-enforced version-tag immutability where available. The workflow's absence check plus concurrency does not block an external registry writer or eliminate an external check/push race. |

Tracked preflight logic can be edited by a repository writer and is not a
replacement for access control or environment approval. Shared concurrency
serializes this repository's publication jobs only; GitHub may replace an older
pending job when another is queued. Review canceled pending runs and retry
deliberately. No registry or GitHub publication was invoked during testing.

## Validation and guidance

### October 2 follow-up: Go dependency updater

[PR #164](https://github.com/wmstipes/The-Foundry-Initiative/pull/164) merged
with successful PR validation; Required Validation, ForgeOps CI, repository
security validation and CodeQL also passed on merge commit
`4ca721196f5b7b215e9792eb7d964196793a424b`.
The subsequent [Dependabot Go update run](https://github.com/wmstipes/The-Foundry-Initiative/actions/runs/37045438055)
failed with `dependency_file_not_resolvable`. It attempted to move `k8s.io/api`
from `v0.36.4` to `v0.37.1` while `k8s.io/client-go` remained at `v0.36.4`;
the older client's fake client imports `k8s.io/api/scheduling/v1alpha2`, which
is absent in the newer API module. This was an updater resolution failure.

The follow-up configuration groups version updates for `k8s.io/api`,
`k8s.io/apimachinery` and `k8s.io/client-go` across patch, minor and major
releases, and excludes them from the generic Go patch group. It leaves
`go.mod`, `go.sum`, security-update grouping and merge controls unchanged.
Local validation passed all 15 repository-policy tests and YAML parsing.
Confirmation that Dependabot produces a resolvable grouped update remains
pending a new update run after this configuration reaches `main`; the
resulting dependency PR must pass the Console checks before merging.

The first run after #167 merged did create
[PR #168](https://github.com/wmstipes/The-Foundry-Initiative/pull/168), with all
three direct Kubernetes modules at `v0.37.1`. However,
[updater run 37049143722](https://github.com/wmstipes/The-Foundry-Initiative/actions/runs/37049143722)
still reported the intermediate `k8s.io/api` resolution error: it processes
group members sequentially, and later successful updates to apimachinery and
client-go also brought api forward. Grouping is not an atomic update operation.

PR #168's initial Linux/Windows Go tests, locked module graph, native candidate
checks, dependency review and container build passed.
[Required Validation](https://github.com/wmstipes/The-Foundry-Initiative/actions/runs/37049257900)
failed only because a Python policy test required the literal
`k8s.io/client-go v0.36.4`; its aggregate gate failed consequently. The repair
requires all three modules to have exact, equal stable-version pins. It retains
the Go runtime constraint and all build, dependency-review and behavior gates.
The old failed runs remain historical evidence. A fresh Dependabot run after
the coordinated module update merges is needed to confirm updater recovery;
live-cluster acceptance of the new client set remains separate from CI.
